# FP8 预填充与量化正确性：推理竞争从算子扩展到可用吞吐

检索窗口：2026-11-20 07:58 至 2026-11-23 07:58（Europe/Zurich，UTC+01:00）；优先最近24小时，扩至72小时。今天的关键判断是：低精度注意力的微基准可以很亮眼，但 KV 重排、精度稳定性和请求组合决定端到端收益；量化权重的加载正确性则是吞吐比较的前提。已检索 DeepSeek、阿里/Qwen、百度、腾讯、字节、国产芯片与学术渠道，以及 NVIDIA、AMD、Intel、Google、AWS、Microsoft 和内存互联厂商的一手发布。国内渠道在窗口内未发现可核实、未重复且达到入选标准的进展，故不凑数。

## 1. FP8 注意力提速受 KV 布局和长序列收益约束

SGLang 社区11月22日提出在 NVIDIA SM120 上接入 FlashInfer `cute-dsl-prims` 的 FP8 预填充路径，仍是功能请求及报告者原型，未成为正式后端。报告者用单张 RTX PRO 6000 Blackwell Workstation、Qwen3.8-27B、FP8 KV、head_dim 256 GQA 测试：相对 FA2，含 KV 收集和 Q 量化的逐层速度在冷启动4k为2.02倍，在60k已缓存加120新 token 为1.27倍；28.8k 冷预填充端到端时间下降8%—15%，141k/221k 提示下降32%/40%。这些是作者自报，不是独立复测，也不能跨硬件外推。[原始议题](https://github.com/sgl-project/sglang/issues/52389)

原部署的 `page_size=1`，原型需先收集为16 token 页或连续缓冲区，每层增加0.05—0.2毫秒；仅限因果注意力、无窗口/soft-cap，图捕获时回退。动态 Q scale 曾使首 token 分布 KL 升至0.08，静态逐层校准约0.013，接近作者所称 FA2 重复运行的0.012。对昇腾的启示是先核对当前 FP8 KV 路径及页布局，再衡量融合或重排的净值。以同模型、相同精度及输出质量门槛，对照现用内核和候选路径，分冷/热前缀测 TTFT、P99、显存峰值、有效吞吐及适配工时；若重排或精度回归抵消收益，应停止迁移。

## 2. 量化配置错配会让服务正常启动却输出错误

SGLang 社区11月22日报告：`compressed-tensors` 的忽略量化名单采用检查点中的未融合层名，而推理层合并为 `qkv_proj`、`gate_up_proj`；在模型未声明相应 `packed_modules_mapping` 时，原本 BF16 的层可能被构造成量化层，权重加载又跳过不匹配参数而不报错。报告者在 RTX A40、LFM2-8B-A1B-AWQ-4bit、GSM8K 200题、温度0.3 条件下，原版得0%，补充融合层名后得89%。GLM-4.5-Air、DeepSeek-V3 类检查点只有 CPU 配置检查，不能把同样错答率推及它们。修复 PR 已提出，状态仍需跟踪。[原始复现](https://github.com/sgl-project/sglang/issues/52209)

这类问题直接影响模型上架和客户信任：服务可用性探针与显存占用都无法识别静默错答。对昇腾应核对模型转换、CANN 算子选择和推理引擎中“忽略量化”规则是否以实际融合层映射闭环，不能预设存在同样缺陷。选代表性 AWQ/MoE 检查点，记录加载参数覆盖率、逐层 dtype 与小规模精度回归；与未量化基线和原框架输出对照，同时记录显存及适配工时。若加载器已严格拒绝缺失权重，问题边界不同。

## 3. AMD 将 FlashInfer API 复用与后端路由绑在一起

AMD 11月20日公布 FlashInfer on ROCm 10.1：在 MI300X/MI325X 与 MI350X/MI355X 上保留上游 v0.6.18 的部分 prefill、decode、MLA 包装接口，通过 `backend="auto"` 在 AITER 与自有 HIP 内核间按调用条件选择；新增 FP8 prefill、POD、融合 MoE 等。官方同时列出限制：gfx950 上 AITER 写入的 OCP FP8 KV 不能由当前 decode 路径直接读取；CUDA 专有 GEMM/XQA 等仍需重写；目前仅支持指定 ROCm 10.1、PyTorch 2.12、Python 3.12 的源码构建组合。这里是厂商发布的功能范围，不代表业务吞吐已验证。[AMD 原文](https://rocm.blogs.amd.com/artificial-intelligence/flashinfer-release3/README.html)

编辑判断：兼容 API 降低上层适配门槛，但数据格式和后端覆盖矩阵决定真正的迁移成本。对昇腾可用同一套代表性 prefill/decode、FP8 KV、MoE 负载建立“可调用—数值正确—可图捕获—性能达标”四级矩阵，核对 CANN 与推理框架已有覆盖；分别统计 TTFT、TPOT、P99、能耗、总成本和适配人日。若格式转换或缺失算子占主导，接口兼容本身不应作为竞争结论。

## 优先验证

1. 用 Qwen3.8 类长短混合流测低精度预填充的端到端净收益，并设输出质量和 P99 不退化门槛。
2. 对 AWQ/MoE 模型增加融合层映射、权重加载覆盖率及小样本精度上线门禁。
3. 汇总三套推理栈的 FP8 KV 格式与算子覆盖矩阵，量化跨后端迁移工时。
